# 性能实测

测试环境：

- `scratch-vm 5.0.300`，Node 24，aarch64。
- 用 `.sb3` 在 VM 里跑，**不是** TurboWarp 编译后的 JS。
- 基准工程把命令放在 `nowarp` 循环里重复执行，用 `timer()` 计时（约 10ms 量化，所以每组重复几十到几百次）。
- 测的是 `run_command` 全流程：命令解析、表达式解析、代数运算、规则化简、打印。

## 典型命令

| 命令 | ms/op（scratch-vm 解释器） |
| --- | ---: |
| `1+1` | 1.1–1.4 |
| `simplify(x+2*x)` | 2.0–2.7 |
| `sqrt(x)^4` | 1.6–1.9 |
| `diff(5^x)` | 1.9–2.5 |
| `diff(sin(x^2))` | 2.4–4.6 |
| `eval(x^2+2*x+1, x=3)` | 3.2–4.2 |
| `subst(x^2, x=(a+1))` | 2.4–2.9 |
| `simplify(sqrt(8))` | 1.8–2.5 |
| `expand((x+1)^3)` | 8.4–9.4 |
| `simplify(subst(x^2, x=(a+1)))` | 3.6–5.4 |

## 规模与瓶颈

| 场景 | 结果 |
| --- | --- |
| `expand((x+1)^10)` | 约 42 ms（二项式定理） |
| `expand((x+y)^10)` | 约 72 ms |
| `expand((x+1)^15)` | 约 79 ms |
| `expand((x+1)^20)` | 约 146 ms，成功 |
| 100 项 `simplify(1+x+...+x)` | 约 59 ms |
| `diff((x+1)^10)` | 约 3 ms 量级 |
| `eval((x+1)^10, x=2)` | 约 3 ms |
| 项目加载 | 约 0.33–0.42 s |

## 结论

1. **交互使用足够快**：课本级表达式在解释器里约 1–5ms。
2. **展开是主要成本，但二项式定理显著改善**；旧实现 `(x+1)^20` 会触及 8192 节点上限。
3. **长和式是第二瓶颈**：主要花在扁平化、同类项合并与 `sig` 字符串比较。
4. **规则引擎固定开销可控**：每条命令至少跑一轮后序重建，规则只在 `sig` 变化时继续，最多 8 轮。
5. 当前实现偏「正确 + 可扩展」，不是高吞吐 CAS：没有 SoA、hash-consing、N-ary 项链表或多项式后端。
6. 在原生 Scratch 的 500ms warp 预算内，`expand((x+1)^20)` 的 146ms 仍然安全。

## 如果继续提速

按收益/风险排序：

1. **多项式后端**：`expand`（以及未来的 `solve`）用「指数 → 系数」数组，避免通用树反复重写。
2. **hash-consing**：用 `sig` 驻留共享子表达式，结构相等变成 ID 相等。
3. **SoA 节点数组**：去掉 `nodes[i].field` 的索引乘法。
4. **N-ary 项链表**：减少加/乘的 flatten / rebuild。
5. **规则索引**：按根节点类型分派规则，避免每条命令扫描全部规则。

## 多项式 GCD / LCM

`gcd` / `lcm` 走 modular 路线：二元 base 的多个采样点、两个素数 CRT、精确 Q 除法验证；n 元再对额外变量做网格采样和张量插值。它是按需命令，比 `simplify` 重，网格点数上限 256。
